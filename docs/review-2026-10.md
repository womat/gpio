### Follow-up: debounce on a Pi

`WithDebounce` had never run on hardware. The new `TestLoopbackDebounce`
(`21f0893`) showed that the package doc was wrong: the debounce delay is
not a constant offset. The Pi has no debounce in hardware, the kernel's
timer counts whole ticks (4 ms at `CONFIG_HZ=250`), so every period up to
4 ms behaves the same and longer ones rise in 4 ms steps. The package doc
and the README were corrected in the same commit; the measured values are
there. CI passed on `21f0893` in all jobs.

### Security

The library takes no input from files, network or the environment; the only
inputs are pin numbers, options and the kernel's events. No exploitable
finding.

- gosec G104 at `rpi/loopback_test.go:61`, `:62`, `:68`: unchecked
  `SetValue`/`Close` in test cleanup — a false alarm; the errcheck exclusion
  for test files in `.golangci.yml` covers the same thing on purpose.
- errorlint, nilerr: no findings.

### Checked, nothing found

- `internal/watch`: `Deliver` sends under the read lock, `Stop`/`Close` close
  under the write lock — no send on a closed channel; double `Stop`/`Close`
  is safe; the `StartFunc` goroutine ends with the watch (except a callback
  that never returns, already under *Not addressed*). The loss accounting
  carries the gap of a dropped event over to the next one correctly. Counter
  overflow is not reachable: `uint64`, and `seqGap` adds at most 2³²−2 per
  event.
- `rpi` data races, by reading (open point of section 0, not measured):
  `gpioLine` and `output` are written before `NewPin` returns and only read
  afterwards, `closed` and `lastSeqno` are atomic, the handler touches only
  the watcher and `lastSeqno`, and it cannot run before `NewPin` returns
  because edges are off until a watch starts. go-gpiocdev's `Line.Close` waits
  for its event goroutine; the handler never blocks, so that cannot hang.
- Constructor error path: if `RequestLine` fails nothing is left behind
  (go-gpiocdev closes its own epoll and eventfd). `Close` releases the line
  even when the `Reconfigure` before it fails.
- `eventTime`: missing timestamp, unreadable clock and `CLOCK_REALTIME`
  stamps fall back to `time.Now()`; a wall-clock step does not affect
  intervals (monotonic reading), the wall time follows within `anchorAge`.
  Pins renewing the anchor at the same time can replace it with one a few
  microseconds older — harmless. `seqGap` handles the wrap of the counter.
- Pin numbers: no panic for any `int` in either backend (`rpi` gets
  go-gpiocdev's `ErrInvalidOffset`).
- Sentinel errors: messages identical to `v1.0.0`, `ErrNilCallback` and
  `ErrClosed` added since `v1.0.3`; all comparable with `errors.Is`.
- Outside this repository: go-gpiocdev's event goroutine panics on an
  unexpected `EpollWait` error (`watcher.go:83`), i.e. not `EBADF`, `EINVAL`
  or `EINTR`. Not seen in practice; noted because it would take a service
  down.

### Still open

- Data races in `rpi` under `-race`: still needs a Go toolchain on a Pi.
- Debounced events up to 11 ms late: not investigated, needs the bench.
- ~~`TestLoopbackDebounce` is flaky on `pi3b`~~ — fixed: `openLoop` read the
  debounced input 10 ms (`settle`) after the change and failed with "input 25
  does not follow output 18" in about one run in ten (1 of 10 on `49c567a`).
  `settle` is now 50 ms; 0 failures of that test in 50 runs of the suite.
- `TestLoopbackPaced` lost edges at 10 kHz once in those 50 runs: 1983 of
  2000 delivered, `DroppedEvents` and `Missed` 0, and a Rising after a
  Rising, so the edges were lost before the kernel numbered them. The test
  comment and the README say nothing is lost at 10 kHz. Not investigated.
- Whether the kernel or the Pi's pinctrl sets a line to input when it is
  released anyway. That decides whether a crash without `Close` leaves an
  output in the same state; to be checked on `pi3b` (kill a process holding
  an output high, read the line with `pinctrl get`).

### Behaviour or internals

- `rpiemu` tests go through `gpio.Pin` and `Drive` throughout; the only
  internal they touch is `defaultBufferSize`, by name. A refactoring breaks
  none of them.
- `internal/watch` tests call `Watcher`'s methods and never its fields. That is
  the internal package's contract, not `gpio.Pin`; merging `Start` and
  `StartFunc` or renaming `Deliver` breaks about 20 tests at compile time.
  Acceptable: the package exists to be tested this way, and `rpiemu` tests the
  same behaviour through the public API, so they would still guard a rewrite.
- `rpi/eventtime_test.go` tests `eventTime` and, in
  `TestEventTimeFollowsWallClockStep`, writes the global `anchor` directly;
  `seqgap_test.go` tests a pure helper. Brittle by nature, the only way off a
  Pi; the proposed `handler` tests are the same kind.
- `gpio_test.go`'s `mockPin` duplicates the compile-time checks both backends
  already have; harmless.

### `rpi`: what only the Pi can test

Needs a line (`RPI_TEST_LINE` or `RPI_TEST_LOOP`): `NewPin` with any option,
`Close`, `SetValue`/`Value` on an open pin, `Number`, `Info`, a successful
`WatchCh`/`WatchFunc`, `StopWatching`, the effect of `WithMode`, `WithPullup`,
`WithDebounce`. `WatchFunc` is never run on the Pi beyond its nil check, and
`WithPullup(PullDown)` nowhere. Runs in CI: `eventTime`, `seqGap`.

The gap is documented — README (*Building and testing*, *Not addressed*) and
`CLAUDE.md` (*Known state*) — and the delivery logic behind it is tested in
`internal/watch`. `TestHandler` from the first finding moves the one piece
with real logic (`handler`) into CI; the rest is calls into go-gpiocdev and
stays on the Pi. Small enough.

### Fuzzing, mutation testing, goleak

None recommended.

- **Fuzzing:** the code with arithmetic (`seqGap`, `eventTime`, the loss
  accounting in `Deliver`) has table tests, and every mutation of `Deliver`
  was caught. A fuzz target with a model of the watcher would be more code
  than `Deliver` itself.
- **Mutation testing:** the 24 hand-made mutations above did the job; a tool
  would be a new install for a one-off.
- **goleak:** a new dependency to check that the `StartFunc` goroutine ends,
  a `for range` over a channel that `Stop` closes (M22 shows the tests notice
  when it is not).

### Side findings outside the tests

Noticed while testing, not part of this section's question; for section 1.
Both *uncertain* whether intended.

- `rpiemu/gpio.go:124`: `WithPullup(gpio.PullUp)` does not change the initial
  level; an input with pull-up reads Low, on a Pi High. The first
  `Drive(Low)` of a test that starts from an idle-high line (an S0 input with
  pull-up) then gives no falling edge, the Pi does. The `NewPin` doc says
  "default state (input, low, no pull)", which does not cover the pull-up
  case.
- `internal/watch/watch.go:45` vs. `rpi/gpio.go:311`: `RisingEdge|4` is accepted
  by `rpiemu` and refused by `rpi` with `ErrInvalidEdgeConfig`.

### Grade

**2 (good).** `internal/watch`, where the concurrency is, caught every
mutation tried, its race tests reproduce the old defects, and the tests are
stable — 50 runs and 24 parallel processes without a failure. Every fix since
the split has a test that fails without it, except `NewPin`'s nil result.
What keeps it from a 1: the `rpi` logic that CI could test runs nowhere but
the Pi, and three `rpiemu` behaviours (debounce with a mask, same level,
event time) survive their removal.
